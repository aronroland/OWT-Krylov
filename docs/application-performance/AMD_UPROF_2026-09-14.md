# AMD uProf profiling, 2026-09-14

## Scope and acceptance

Fresh SpecWave Limon application executions using AMD uProf 5.3.521.0 on the
Ryzen 7 PRO 7840U: four MPI ranks, double precision, 1,778 vertices,
36-by-36 spectra, all 36 timesteps. This is not production-scale qualification,
archived-reference validation, or figure regeneration.

The profiler retry began with `perf_event_paranoid=0` and `kptr_restrict=0`.
These settings had changed outside this workflow after the earlier failed
attempt. This work does not change them or restore an older user setting.

The retained current-source executable is
`runs/limon-uprof-hotspots-20260914/bin/ww-x`, with its adjacent build manifest.
No numerical kernel, stopping tolerance, physics, or compiler arithmetic option
was changed during profiling. Each collection is preceded by a fresh
unprofiled same-binary reference and checks all timesteps, final owned-state
coverage, finite/nonnegative spectra, bitwise equality, and operation counts.
All measurements include cold ST4 table construction because each sample starts
in its own repository-owned case directory.

## Reproduction

Run from OWT-Krylov, using a new run ID each time:

```bash
bash benchmarks/specwave_limon.sh --run-id limon-uprof-hotspots-retry-20260914 \
  --ranks 4 --amd-uprof /opt/AMDuProf_5.3-521 \
  --baseline docs/application-performance/runs/limon-uprof-hotspots-20260914/bin/ww-x
bash benchmarks/specwave_limon.sh --run-id limon-uprof-assess-20260914 \
  --ranks 4 --amd-uprof /opt/AMDuProf_5.3-521 --uprof-config assess \
  --baseline docs/application-performance/runs/limon-uprof-hotspots-20260914/bin/ww-x
bash benchmarks/specwave_limon.sh --run-id limon-uprof-ibs-20260914 \
  --ranks 4 --amd-uprof /opt/AMDuProf_5.3-521 --uprof-config ibs \
  --baseline docs/application-performance/runs/limon-uprof-hotspots-20260914/bin/ww-x
```

These IDs identify retained evidence, not directories to overwrite. Collection
commands, input hashes, source/build manifests, binding logs, host snapshots,
per-step solves and final spectra are retained in each run. AMD raw sessions
and internal logs remain on disk, ignored by Git. CLI reports and file hashes
are retained separately. Profiled wall times include sampling overhead and are
not baseline/candidate speedup measurements.
The first two runs used the then-default detailed source report. With the
current runner, add `--uprof-detail` to reproduce that report depth; without
it, the same collection produces a lighter function-summary report. The
detailed Assess report completed successfully but required about nine minutes
and reached roughly 21 GB resident memory during postprocessing. That cost
is AMD reporting overhead, not application execution time.

## Hotspots findings

[Report](runs/limon-uprof-hotspots-retry-20260914/profile-00/uprof-report.csv),
[accepted application results](runs/limon-uprof-hotspots-retry-20260914/results.json).
Collection and report generation both exited successfully. Every rank has
nonzero sampled CPU time. Both runs completed 721 iterations with maximum true
relative residual 9.72698039e-9 against the configured 1e-8 tolerance. Final
spectra and per-step work counts were identical.

The following percentages are shares of sampled CPU time summed over all four
ranks and the whole application, not percentages of wall-clock solver time:

| Function | Exclusive CPU share | Inclusive CPU share |
| --- | ---: | ---: |
| Split local SSOR `apply` | 18.01% | 20.02% |
| Pipelined BiCGSTAB, including its callees | 5.71% | 56.92% |
| Local dot product | 3.49% | 3.49% |
| Spectral coupling `add` | 3.54% | 5.08% |
| `MPI_Bcast` | 0.00% | 22.00% |
| ST4 `calc_TABU_TAUHFT2` | 2.36% | 7.30% |

Inclusive rows overlap and must not be added. AMD's `--show-percentage` option
prints percentages even in the column named `TOTAL_CPU_TIME (s)`.

The broadcast cost needs context: `TABU_TAUHF.hpp` constructs the cold lookup
table only on rank zero, then calls `dd.Bcast(TAUHFT2)` on every rank. The
report attributes lookup-table construction to rank zero and about 7.33% of
global inclusive CPU time in `MPI_Bcast` to each other rank. This strongly
indicates startup waiting. It is not evidence that Krylov reductions consume
22% of runtime, nor a measurement of network bandwidth or transfer time.

The report resolves numerical functions, but some system-library functions
remain module/offset symbols, and the AMD log records unsuccessful `[vdso]`
symbol lookup. Call-stack attribution is sampling evidence, not an exact
MPI-call trace or critical-path measurement.

## Hardware-counter findings

[Assess report](runs/limon-uprof-assess-20260914/profile-00/uprof-report.csv),
[accepted application results](runs/limon-uprof-assess-20260914/results.json).
Both collection and reporting exited zero. All four ranks have nonzero cycle
samples. Both application runs completed 721 iterations with maximum true
relative residual 9.72698039e-9, bitwise-identical spectra, and matching work
counts. The report-coverage checks for Hotspots and Assess passed in
`runs/uprof-report-gates-v3-20260914/`.

Selected entries from AMD's overall-assessment function table:

| Function or inlined attribution | Sampled cycle share | Reported IPC |
| --- | ---: | ---: |
| Split local SSOR `apply` | 21.22% | 0.5638 |
| Pipelined BiCGSTAB body | 6.68% | 0.3675 |
| Local dot product | 5.40% | 0.5620 |
| SIMD coefficient multiply/add | 5.04% | 0.5093 |
| Spectral coupling `add` | 3.08% | 3.3948 |

These are exclusive sampled-cycle attributions across the application, not
inclusive solver times or wall-clock percentages. Inlined intrinsic entries
also exist and must not be assigned to a parent without checking their context.
The low reported IPC in several streaming numerical kernels motivates memory
access investigation, but does not by itself prove a bandwidth limit.

AMD reports 27.8190 for SSOR's `%L1_DC_MISSES` metric. Its own event definition
includes hardware and software prefetch requests, so this must not be presented
as the percentage of application loads that missed L1. Likewise, the sampled
misalignment counter is a reason to inspect actual buffer addresses and IBS
data, not proof that every borrowed array is misaligned. Do not infer exact
bandwidth, energy use, or thermal throttling from these profiles.

## IBS findings

[IBS report](runs/limon-uprof-ibs-20260914/profile-00/uprof-report.csv),
[accepted application results](runs/limon-uprof-ibs-20260914/results.json),
[rank coverage](runs/limon-uprof-ibs-20260914/profile-00/uprof-ranks.json).
Collection and summary reporting exited zero. All four ranks have nonzero IBS
operation samples. The same 36-step acceptance checks passed, with 721
iterations, maximum true relative residual 9.72698039e-9, identical final
spectra, and matching work counts.

| Function | Sampled load L1 miss rate | Average sampled L1 load-miss latency |
| --- | ---: | ---: |
| Split local SSOR `apply` | 46.8642% | 312.3701 cycles |
| Local dot product | 71.1357% | 224.0175 cycles |
| Spectral coupling `add` | 1.0035% | 138.8595 cycles |

These are AMD's `IBS_LD_L1_DC_MISS_RATE_%` and
`IBS_LD_L1_DC_MISS_LAT_AVE` metrics, using the definitions embedded in the CSV.
Latency is averaged only over sampled load misses, not every load. Samples do
not establish exact counts for all executed loads, and the latency sums are
not non-overlapping wall-clock stall times. In particular, these metrics do
not identify all misses as DRAM accesses or prove saturated memory bandwidth.

Together with the SSOR cycle share and low IPC, the IBS observations make
SSOR memory access and repeated vector streaming concrete optimization targets.
The much lower sampled miss rate in spectral coupling is a useful contrast;
it argues against treating all numerical kernels as one uniform bottleneck.

## Next optimization targets

1. Prioritize SSOR and spatial/vector memory access in OWT-Krylov. SSOR is the
   largest individual numerical hotspot and IBS shows costly sampled load
   misses. Measure actual buffer alignment and coefficient/workspace reuse
   before choosing a layout or pass-count change. Preserve support for borrowed
   unaligned application storage. The previously rejected SSOR tiling change
   stays rejected.
2. Separate cold-start table construction from steady integration profiling.
   SpecWave already has a validated ST4 table cache; startup improvements belong
   to the application, not the external Krylov library.
3. Measure halo and reduction critical paths on the intended production mesh
   and machine. Whole-application OpenMPI CPU samples on one workstation do
   not establish a multi-node scaling bottleneck.

No production-scale speedup is established by these profiles.
